# x402 — pay for a premium agent CV with testnet USDC

## What x402 is

x402 is an open payment standard built on the HTTP `402 Payment
Required` status code. A server returns 402 with payment details, a
client pays with crypto, and the server serves the resource after
verifying the payment. It was originally developed by Coinbase and
is now maintained by the x402 Foundation (x402.org). Payment becomes
a property of the request itself — no account, no API key, no
subscription.

The flow:

1. The client requests a paid resource.
2. The server responds with `402 Payment Required`, including a
   `PAYMENT-REQUIRED` header with a base64-encoded
   `PaymentRequired` object (accepted schemes, price, network,
   destination).
3. The client signs a payment payload and retries with a
   `PAYMENT-SIGNATURE` header.
4. The server verifies the payment (directly or through a
   facilitator) and returns the resource with a `PAYMENT-RESPONSE`
   header.

## x402 on NEAR — it exists

x402 v2 supports NEAR natively:

- Network IDs: `near:mainnet` and `near:testnet` (CAIP-2).
- Token: any NEP-141 token. The payer signs a NEP-366
  `SignedDelegate` authorizing `ft_transfer`.
- The facilitator relayer sponsors NEAR gas and the required `1`
  yoctoNEAR deposit, so the payer spends only the NEP-141 token
  amount.

FastNEAR ships `@fastnear/x402` — adapters for the official
`@x402/near` exact-payment mechanism, using x402 v2, NEP-366
signed delegate actions, and the Foundation's NEAR verifier and
settlement code. There are public reference facilitators (verified
2026-09-24):

| Network | Facilitator | Circle USDC asset |
|---|---|---|
| `near:mainnet` | `https://x402.mikedotexe.com` | `17208628f84f5d6ad33f0da3bbbeb27ffcb398eac501a31bd6ad2011e36133a1` |
| `near:testnet` | `https://test.x402.mikedotexe.com` | `3e2210e1184b45b64c8a434c0a7e7b23cc04ea7eb7a6c3c32520d03d4afcb8af` |

Each serves `GET /supported` publicly; `POST /verify` and `POST
/settle` require a per-instance `X-API-Key`, approved manually per
resource-server instance and environment. Keys belong in server-side
secret storage; payers never need one.

Testnet USDC is free from the Circle faucet (faucet.circle.com,
NEAR Testnet). A buyer needs testnet USDC and a full-access key.

## What Genesis built

**One endpoint: `GET /api/agent-premium?token_id=<agent>`.** A
premium agent CV — the agent's full onchain record (Core
`get_agent`) + league standing + full match history and earnings
breakdown — paid for in testnet USDC. This is the agent EARNING
via x402: the payment goes to the Genesis treasury.

- **Price:** 0.01 testnet USDC (10000 smallest units, 6 decimals).
  A demo price, so anyone can try it with faucet funds. Testnet
  USDC has no real value.
- **Network:** `near:testnet`. **Asset:** testnet USDC, contract
  `3e2210e1184b45b64c8a434c0a7e7b23cc04ea7eb7a6c3c32520d03d4afcb8af`.
  **Recipient:** the Genesis treasury testnet account,
  `genesisdemo354551.testnet`.
- **402 response:** `PAYMENT-REQUIRED` header with a base64 x402 v2
  `PaymentRequired` object (scheme `exact`, network
  `near:testnet`, amount, asset, recipient, expiry), plus the same
  requirements and step-by-step payment instructions in the JSON
  body.

## How payment is verified (self-facilitation)

The full NEP-366 SignedDelegate flow goes through a facilitator,
and the hosted reference facilitator's `/verify` and `/settle`
require an API key approved manually per instance. Genesis does not
have that key, so this route **self-facilitates**: it verifies the
payment directly onchain.

1. The payer sends 0.01 testnet USDC to the treasury with a normal
   `ft_transfer` on the testnet USDC contract (from their wallet).
2. The payer retries the endpoint with
   `?paymentTx=<transaction hash>&paymentSender=<their account>`.
3. The route fetches the transaction from the NEAR testnet RPC
   (`tx` method) and checks:
   - the transaction succeeded onchain;
   - it contains an `ft_transfer` on the testnet USDC contract
     sending >= 0.01 USDC to the treasury.
4. The tx hash is recorded (`demo/x402-payments.json` +
   in-memory set) so one payment buys exactly one access. A reused
   tx hash gets a 402 again.
5. Verified → 200 with the premium CV + a `PAYMENT-RESPONSE`
   header (base64 settlement object). Not verified → 402 again.

**No payment, no content.** If no real payment is verified, the
endpoint returns 402, never the premium CV. Nothing is faked: the
payment is real testnet USDC, verified against the chain.

## What is real vs what is not

- **Real:** the 402 with a proper x402 v2 `PaymentRequired`
  object; the testnet USDC payment (real tokens, real chain);
  the onchain verification (RPC `tx` lookup, success + ft_transfer
  check); the one-payment-one-access dedup; the premium CV content
  (real onchain agent record).
- **Simplified, and labelled as such:** the payment proof is a
  transaction hash, not a NEP-366 SignedDelegate. The full
  delegate flow (payer signs a delegate, facilitator verifies and
  settles it) is the production path and needs a facilitator API
  key — a manual approval. This route verifies the payment
  directly onchain instead, which is the x402-sanctioned
  self-facilitation path. The payment itself is identical (an
  `ft_transfer` of testnet USDC to the treasury); only the proof
  format differs.
- **Not built:** a hosted facilitator integration, a client-side
  x402 wallet flow (the payer uses their own wallet to send the
  USDC), and an "agent pays via x402" client. The agent-pays
  direction is the natural next step: a Genesis agent with a
  testnet USDC balance could pay another agent's premium endpoint
  the same way.

## How to test (small, real, free)

1. Get free testnet USDC from the Circle faucet
   (faucet.circle.com → NEAR Testnet) into a testnet wallet.
2. `GET /api/agent-premium?token_id=genesis-gen-3` → 402 with the
   payment requirements.
3. Send 0.01 testnet USDC to `genesisdemo354551.testnet` with
   `ft_transfer` on
   `3e2210e1184b45b64c8a434c0a7e7b23cc04ea7eb7a6c3c32520d03d4afcb8af`.
   (Or with the NEAR CLI: `near contract call-function as-transaction
   <usdc-contract> ft_transfer json-args '{"receiver_id":
   "genesisdemo354551.testnet", "amount": "10000"}' prepaid-gas
   '100.0 Tgas' attached-deposit '0.000000000000000000000001 NEAR'
   sign-as <your-account> network-config testnet`.)
4. Retry the endpoint with `?paymentTx=<tx hash>&paymentSender=<your
   account>` → 200 with the premium CV.
5. Retry with the same tx hash → 402 (already used).

Run the tests with no funds at all: `node test/x402.cjs`.
