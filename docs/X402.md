# x402 — the payment rail for every Genesis transaction

## The rule

Every Genesis onchain action — mint, trade (buy), breed, evolve —
and the premium agent CV goes through the 402 payment rail. That is
the main purpose of Genesis: an agent economy where every
transaction is a paid API call. No action runs without a verified
payment; no payment, no action. See `docs/ACTIONS-402.md` for the
action endpoint and curl examples.

## What x402 is

x402 is an open payment standard built on the HTTP `402 Payment
Required` status code. A server returns 402 with payment details, a
client pays with crypto, and the server serves the resource after
verifying the payment. It was originally developed by Coinbase and
is now maintained by the x402 Foundation (x402.org). Payment becomes
a property of the request itself — no account, no API key, no
subscription.

The flow:

1. The client requests a paid resource.
2. The server responds with `402 Payment Required`, including a
   `PAYMENT-REQUIRED` header with a base64-encoded
   `PaymentRequired` object (accepted schemes, price, network,
   destination).
3. The client pays and retries with proof (`PAYMENT-SIGNATURE`
   header, or a transaction hash).
4. The server verifies the payment (directly or through a
   facilitator) and returns the resource with a `PAYMENT-RESPONSE`
   header and an ed25519 signed receipt.

## Two rails in every 402

Every Genesis 402 offers **two rails in one `accepts` list** —
seven entries total. **Near-intents is PRIMARY (first, 6 entries);
exact is SECONDARY (last, 1 entry).** The same object goes in the
`Payment-Required` header and in the JSON body, so header
truncation cannot hide it.

### Primary rail — near-intents (any chain → USDC on NEAR)

One `exact` entry per origin asset, `scheme: 'exact'`,
`extra.assetTransferMethod: 'near-intents'`, `paymentFlow:
'upfront'`:

| Origin | Network (CAIP-2) | Asset (x402) | Route minimum |
|---|---|---|---|
| Ethereum USDC | `eip155:1` | `0xa0b86991c6218b36c1d19d4a2e9eb0ce3606eb48` | ~0.30 USDC |
| Arbitrum USDC | `eip155:42161` | `0xaf88d065e77c8cc2239327c5edb3a432268e5831` | ~0.0053 USDC |
| Base USDC | `eip155:8453` | `0x833589fcd6edb6e08f4c7c32d4f71b54bda02913` | ~0.15 USDC |
| Solana USDC | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` | ~0.094 USDC |
| Ethereum ETH | `eip155:1` | `slip44:60` | ~0.30 USDC |
| Solana SOL | `solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp` | `slip44:501` | ~0.094 USDC |

The destination is USDC on NEAR mainnet (contract
`17208628f84f5d6ad33f0da3bbbeb27ffcb398eac501a31bd6ad2011e36133a1`)
to the Genesis mainnet funding account (`INTENTS_FUNDING_ACCOUNT`).
The flow is Penstock's 2-step dance
(ace-coderr/penstock, `packages/intents-adapter/src/method.ts`):

1. **Quote.** The client sends `PAYMENT-SIGNATURE`
   `{type:'quote', refundTo}` (base64 JSON, in the
   `?paymentSignature=` query param or the `PAYMENT-SIGNATURE`
   header). The server asks 1Click for an `EXACT_OUTPUT` quote —
   deliver the action price as USDC on NEAR, `refundTo` = the
   payer on the origin chain — and **verifies the quote's ed25519
   signature** (mirroring the official 1Click SDK check, with
   `node:crypto` only) before using its deposit address. A quote
   that fails the signature check is refused outright.
2. The server answers with a **second 402** whose quoted entry
   has `payTo` = the single-use deposit address, `amount` =
   `amountIn`, `refundDeadline`, and an **HMAC operation token**
   bound to deposit + resource + destination + expiry
   (`<keyId>.<expiry>.<mac>`, Penstock's `token.ts` shape).
3. **Deposit.** The payer deposits on the origin chain, then
   sends `PAYMENT-SIGNATURE` `{type:'deposit', operationToken,
   depositAddress, txHash}`. The server verifies the token
   (constant-time), **polls `GET /v0/status` until `SUCCESS` /
   `REFUNDED` / `FAILED`** (bounded, ~25s per call; a still-pending
   deposit gets a 402 with `Retry-After: 5` — retry with the same
   deposit), and only then runs the paid action, **exactly once**
   (dedup by operation instrument + payments log).
4. Settled → 200 with the result + an **ed25519 signed receipt**
   (canonical JSON: `paymentId, action, amount, both tx hashes,
   payer, timestamp, simulated` flag) + a `PAYMENT-RESPONSE`
   header. The receipt verifies offline with `verifyReceipt()` in
   `api/near-intents-rail.js` — no server needed.

**Server terms always come from the server's own offers.** A
presented `accepted` entry is only used to pick one of them; a
tampered price, payee or asset is refused.

### Secondary rail — exact (testnet USDC, self-facilitated)

One entry, `scheme: 'exact'`, network `near:testnet`, asset testnet
USDC (`3e2210e1184b45b64c8a434c0a7e7b23cc04ea7eb7a6c3c32520d03d4afcb8af`),
recipient the Genesis treasury testnet account
(`genesisdemo354551.testnet`). The payer sends testnet USDC with a
normal `ft_transfer` (free from the Circle faucet,
faucet.circle.com, NEAR Testnet), then retries with
`?paymentTx=<transaction hash>&paymentSender=<their account>`. The
server verifies the payment directly onchain (RPC `tx` method):
the transaction succeeded and contains an `ft_transfer` of >= the
price to the treasury. The hash may be pasted in 64-hex or base58
(as Nearblocks shows it) — both canonicalise to the same hex hash,
so one payment cannot be spent twice by pasting it in the other
form. One tx hash buys exactly one action.

This rail exists so transactions can still complete while 1Click's
NEAR solvers are down (see "Blocked" below). It is the working
path today.

## Prices

The 402 price is the **service fee for executing the action**; the
treasury covers the underlying testnet NEAR costs (birth 0.5 NEAR,
mint 0.1 NEAR, listing price on buy).

| Action | Exact rail (testnet USDC) | Near-intents rail (mainnet USDC) |
|---|---|---|
| mint | 0.05 | 0.50 |
| breed | 0.05 | 0.50 |
| evolve | 0.01 | 0.35 |
| buy | 0.05 fixed demo, or the listing's NEAR price converted by a 1Click dry quote when it works | 0.50, or the dry-quote conversion when it works |
| premium CV | 0.01 | 0.35 |

Testnet prices are small demo prices in free faucet USDC. Mainnet
prices are higher because they are real money and must clear
1Click's per-route bridge minimums (Ethereum USDC ~0.30 USDC is the
highest offered). A payment below the origin route's minimum is
refused by 1Click ('Amount is too low for bridge') — the rail
passes that real error through.

## Modes

`mode=` on the action endpoint (default `live`); never mixed.

- **live** — real payments, real onchain execution.
- **dry** — near-intents quotes are dry (price preview, no deposit
  address, no funds can move); the exact rail still verifies for
  real and actions execute for real.
- **demo** — everything simulated, no network: a `sim:...` payment
  is accepted and the action returns a simulated result with `sim:`
  tx hashes. Labelled `simulated: true` everywhere (response,
  receipt, log).

## What is real vs what is not

- **Real:** the 402 with a proper x402 v2 `PaymentRequired`
  object on both rails; the testnet USDC payment (real tokens, real
  chain) and its onchain verification; the near-intents quote
  signature check, HMAC operation tokens, and 1Click status
  polling (all real, against the live 1Click API); the one-payment-
  one-action dedup; the onchain action execution (real testnet txs);
  the ed25519 signed receipts (verifiable offline).
- **Simplified, and labelled as such:** the exact rail's payment
  proof is a transaction hash, not a NEP-366 SignedDelegate. The
  full delegate flow (payer signs a delegate, facilitator verifies
  and settles it) is the production path and needs a facilitator
  API key — a manual approval. This route verifies the payment
  directly onchain instead (x402-sanctioned self-facilitation).
  The payment itself is identical; only the proof format differs.
- **Not built:** a hosted facilitator integration; a client-side
  x402 wallet flow (the payer uses their own wallet to send the
  USDC); prepaid sessions (Penstock's answer to route minimums —
  out of scope for this build).

## Honest limits

- **BLOCKED — 1Click NEAR quoting is down.** Verified live
  2026-11-05 16:08 WAT: every pair touching NEAR returns HTTP 400
  'Quoting for this pair is not available' (only non-NEAR pairs
  quote). A live near-intents swap CANNOT complete until the NEAR
  solvers return. The rail passes 1Click's real error through and
  never invents a quote; dry mode still proves the flow end to end.
  The exact rail is the working path until then.
- **1Click is mainnet-only, no testnet.** The near-intents rail
  settles in MAINNET USDC to the funding account; the Genesis
  actions execute on NEAR TESTNET (the treasury covers the testnet
  NEAR costs). The mainnet USDC is the payment for the action; the
  testnet NEAR is the cost of executing it.
- **The mainnet funding account does not exist yet.**
  `INTENTS_FUNDING_ACCOUNT` is unset. Live near-intents quotes are
  refused with a clear error until it is created and set (Isaiah's
  step, ~0.1 NEAR). Dry quotes use the placeholder
  `genesis-funding.near` and work today.
- **Live near-intents settlement needs `OPERATION_TOKEN_SECRET`**
  set in Vercel env.** Without it the rail refuses to mint
  operation tokens (and therefore refuses live settlement) with a
  clear error instead of silently using a weak secret.
- **Exactly-once is per serverless instance** (in-memory set) plus
  a best-effort payments log (`demo/x402-actions.json` for actions,
  `demo/x402-payments.json` for the premium CV). Vercel's
  filesystem is read-only, so a replay across cold instances is
  NOT blocked by this code — the durable proof is the 1Click
  deposit instrument (one deposit address settles once) and the
  onchain action. A shared store is the production path.
- **Quote signatures depend on the one published 1Click manager
  key** (`ed25519:reYaWhvwu8Jzo3WUM3zhn6VrhuMEF4eADL17qtRVifc`).
  If 1Click rotates it, quotes fail closed (no payment proceeds)
  until the key is updated here.
- **If an action becomes invalid between payment and execution**
  (the window is seconds), the payment is NOT marked spent, so the
  same tx hash / operation can be presented again for a corrected
  action — but the USDC already reached the treasury and is not
  auto-refunded. The 402 is only offered for a currently valid
  action; validate before you pay.
- **Testnet USDC has no real value.** The exact-rail prices are
  demo prices so anyone can try them with faucet funds.

## How to test

Exact rail (real, free, works now) — see `docs/ACTIONS-402.md`
for the curl examples, and `test/agent-action.cjs` (45 checks,
mocked, no funds) plus `test/near-intents-rail.cjs` (30 checks)
plus the original `test/x402.cjs` (11 checks, the premium
endpoint's regression suite).

Near-intents rail in dry mode (real 1Click dry quotes, no funds):
`GET /api/agent-action?action=mint&token_id=genesis-visitor-4&mode=dry`
then present a quote payload for the Arbitrum USDC offer — the
server returns the quoted 402 (or 1Click's real error while the
NEAR solvers are down).
